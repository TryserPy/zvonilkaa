# Звонилка

Видеозвонки один на один прямо в браузере: сквозное шифрование, камера и
демонстрация экрана одновременно, показ пинга и качества канала. Без
регистрации, установки и внешних зависимостей.

---

## Запуск

### Windows — двойным кликом

Запустите **`start.bat`**. Скрипт поднимет сервер и попробует вывести его
наружу — по очереди через туннели Cloudflare (QUIC, затем http2), Pinggy и
localhost.run. Первый рабочий побеждает, и вы получаете готовую ссылку,
уже скопированную в буфер обмена:

```
  Ссылка для собеседников (работает из любой сети):
      https://mellow-river-4821.trycloudflare.com
```

Эту ссылку отправляете собеседнику — и он подключается откуда угодно, хотя
сервер работает на вашем компьютере. Останавливается по Ctrl+C.

Если все туннели заблокированы (так бывает — некоторые провайдеры режут их
по DPI), скрипт сам переключается на собственный HTTPS и показывает адреса
вида `https://192.168.1.15:3000`. По ним можно звонить внутри своей сети —
Wi-Fi, кабель или VPN вроде Radmin и Hamachi. Браузер один раз предупредит о
самоподписанном сертификате: «Дополнительно» → «Перейти на сайт».

Дополнительно:

```
start.bat -Port 8080     другой порт
start.bat -Local         сразу локальный HTTPS, без попыток туннеля
```

### Вручную, на любой системе

```bash
node server.js
```

Откройте `http://localhost:3000`. `npm install` не нужен, зависимостей нет
(минимальный WebSocket-сервер реализован в `lib/ws.js`).

Нужен Node.js 18 или новее. Порт меняется переменной `PORT`:

```bash
PORT=8080 node server.js
```

С ключом `--https` сервер сам выпишет самоподписанный сертификат на все
адреса компьютера и поднимется по HTTPS — это нужно, чтобы камера и микрофон
работали не только на `localhost`:

```bash
node server.js --https
```

Сертификат сохраняется в `certs/` и переиспользуется, так что предупреждение
браузера придётся пропустить только один раз. Если у вас есть настоящий
сертификат, положите его туда же как `cert.pem` и `key.pem` — он будет
использован вместо самоподписанного.

## Как пустить в звонок людей из других сетей

Сервер на вашем компьютере слушает `localhost` — снаружи его не видно. Дать к
нему доступ можно тремя способами.

1. **Туннель** — то, что делает `start.bat`. Ничего настраивать не надо,
   сервер остаётся у вас, HTTPS выдаётся автоматически. Вручную:

   ```bash
   cloudflared tunnel --url http://localhost:3000
   ssh -p 443 -R0:localhost:3000 a.pinggy.io
   ssh -R 80:localhost:3000 nokey@localhost.run
   ```

   Туннели иногда блокируют на уровне провайдера. Признак в логе
   `cloudflared` — обрыв TLS-рукопожатия (`TLS handshake with edge error:
   EOF`) или таймаут QUIC. Тогда помогает только смена канала: раздача с
   телефона, VPN или хостинг.

2. **VPN между участниками** — Radmin VPN, Hamachi, Tailscale. Все попадают в
   одну виртуальную сеть, и работает обычный локальный адрес с `--https`.
   Ничего пробрасывать не нужно.

3. **Проброс портов на роутере** — нужен «белый» IP. У многих провайдеров его
   нет, так что способ рабочий, но капризный.

4. **Хостинг** — самый надёжный вариант: ничего не блокируется, адрес
   постоянный, компьютер можно выключать. Пошаговая инструкция для Render
   и Docker — в [DEPLOY.md](DEPLOY.md).

Через ваш компьютер при этом идут только служебные данные — пара килобайт на
установку связи. Видео и звук передаются напрямую между собеседниками, так что
ни канал, ни процессор нагрузки не почувствуют.

## Как это работает

```
Браузер A  ←── WebSocket, зашифрованный ключом из ссылки ──→  Сервер  ←──→  Браузер B
    └──────────────── видео и звук напрямую, DTLS-SRTP ─────────────────────────┘
```

Сервер выполняет роль «телефонистки»: помогает двум браузерам найти друг друга
и отходит в сторону. Медиапоток идёт напрямую между устройствами, а служебный
обмен зашифрован ключом, которого у сервера нет, — прослушать или записать
разговор он не может ни при каком раскладе.

## Безопасность

Три независимых слоя, каждый закрывает свою угрозу.

**Медиапоток — DTLS-SRTP.** Обязательное сквозное шифрование WebRTC. Ключи
вырабатывают сами браузеры, они никогда не покидают устройства. Шифр виден в
панели «Качество соединения».

**Сигналинг — AES-GCM ключом из ссылки.** Ссылка выглядит так:

```
https://пример/abcd-efgh-ijkl#k=<256-битный ключ>
```

Часть после решётки браузер по правилам HTTP на сервер не отправляет никогда.
Этим ключом шифруется всё, чем обмениваются участники: SDP, ICE-кандидаты,
состояние микрофона и камеры. Сервер видит только шифротекст — прочитать
описание сессии или подменить отпечатки сертификатов он не может, а значит не
может и встать посередине. Если ссылки у собеседников разные, звонок не
поднимется и обе стороны увидят понятное объяснение.

**Код безопасности.** Короткий отпечаток из сертификатов обеих сторон
(SHA-256). Совпадает у вас и у собеседника — посредника нет. Смотрите в
панели статистики.

Заголовки: строгая `Content-Security-Policy` (страница не ходит никуда, кроме
себя), запрет встраивания в чужой iframe, `Permissions-Policy` отдаёт камеру,
микрофон и захват экрана только самой странице и отбирает всё остальное,
`Referrer-Policy: no-referrer`, HSTS при работе по HTTPS. Сервер ограничивает
число новых соединений и сообщений с одного адреса.

Код комнаты — 12 знаков из алфавита без похожих букв, это около 60 бит:
перебрать комнату наугад нереально, а с учётом ключа в ссылке — бессмысленно.

## Возможности

| | |
|---|---|
| Камера и экран вместе | Четыре потока в звонке: ваши камера и экран, камера и экран собеседника |
| Выбор главного окна | Клик по миниатюре разворачивает любой поток на весь экран, в том числе свой |
| Микрофон | Включение и выключение, состояние видно собеседнику |
| Камера | Включение и выключение, выбор устройства прямо в звонке |
| Демонстрация экрана | Окно, вкладка или весь экран, до 1080p и 60 к/с, вместе со звуком |
| Режимы демонстрации | «Чёткость» для текста и кода, «Плавность» для видео и игр |
| Звук собеседника | Отключается одной кнопкой, вывод переключается на наушники |
| Шумоподавление | Шум, эхо и автоусиление громкости — переключаются на лету |
| Проверка звука | Видно, уходит ли ваш голос и приходит ли голос собеседника |
| Кто говорит | Подсветка говорящего и уровень своего микрофона на кнопке |
| Пинг | Round-trip time, обновляется каждую секунду |
| Статистика | Буфер приёма, ощущаемая задержка звука, потери, джиттер, битрейт, разрешение, кодек, маршрут |
| Чат | Сообщения напрямую собеседнику, мимо сервера |
| Имена | Своё имя на плитках, в чате и в уведомлениях |
| Журнал | История событий соединения и ошибок, копируется одной кнопкой |
| Перезапуск у обоих | Пересобирает связь сразу на двух устройствах |
| Ссылка-приглашение | Копирование в буфер или системное «Поделиться» |
| Тема | Светлая и тёмная, следует настройкам системы |

На телефоне: подписи под кнопками, настройки открываются шторкой снизу,
демонстрация экрана скрывается там, где браузер её не умеет, а на своём окне
появляется кнопка переключения фронтальной и основной камеры. Полезные
настройки — шумоподавление, эхоподавление, автоусиление, звук демонстрации и
низкая задержка — включены сразу.

**Горячие клавиши:** `M` — микрофон, `V` — камера, `D` — демонстрация экрана,
`A` — звук собеседника, `C` — чат, `K` — настройки, `S` — статистика, `F` —
во весь экран, `R` — переподключить связь, `E` — завершить, `1`–`4` — выбрать
главное окно. Работают и в кириллической раскладке; полный список есть в настройках.

## Чат

Сообщения идут по каналу данных WebRTC — то есть напрямую собеседнику и под
тем же шифрованием DTLS, что и видео. Сервер их не видит вовсе. История нигде
не сохраняется и исчезает вместе со звонком: обновили страницу — переписки
больше нет.

Текст выводится через `textContent`, поэтому разметка из сообщения остаётся
текстом и никогда не исполняется.

## Имя

Задаётся в лобби или в настройках, запоминается в браузере и передаётся
собеседнику вместе с состоянием микрофона и камеры. Видно на плитках, в
кружке вместо аватарки, в чате и в сообщениях о входе и выходе. Не задали —
будет «Собеседник».

## Как устроены потоки

В соединении заранее создаются четыре дорожки в фиксированном порядке:
микрофон, камера, экран, звук экрана. Дорожка опознаётся по её месту, поэтому
камеру и демонстрацию можно включать и выключать без переговоров о
соединении — картинка появляется мгновенно и связь не прерывается.

Дорожки создаёт только тот, кто первым вошёл в комнату. Так вышло не случайно:
по спецификации транссиверы, созданные через `addTransceiver`, не
переиспользуются при входящем оффере, и если бы их создавали обе стороны,
получилось бы восемь потоков вместо четырёх. Второй участник подхватывает
готовые дорожки после применения оффера.

## Если звука нет

В настройках есть блок «Проверка звука» — он отвечает на вопрос сразу, без
гаданий:

* **Ваш микрофон** — полоска движется, когда вы говорите. Не движется —
  выбран не тот микрофон или он приглушён в системе.
* **Вас слышно** — сколько килобит в секунду реально уходит собеседнику.
  «Нет сигнала» значит, что голос не покидает ваш компьютер.
* **Звук собеседника** — сколько приходит обратно.

Отдельная история — блокировка автовоспроизведения. Браузер не даёт запустить
звук, пока по странице не кликнули; в этом случае вверху появляется кнопка
«Нажмите, чтобы включить звук». Любой клик по экрану тоже снимает блокировку.

Звук собеседника воспроизводится тем же элементом, что и его видео, а не
отдельным `<audio>`. Так надо: Safari на iOS через отдельный аудиоэлемент
поток из WebRTC просто не проигрывает, и это выглядит как «меня никто не
слышит».

## Если пропал выбор динамиков

Список устройств вывода ведёт себя по-разному в разных браузерах: Chrome
отдаёт его сразу после разрешения на микрофон, Firefox — только по явному
запросу (появляется кнопка «Выбрать устройство»), Safari переключать вывод не
умеет вовсе. Поле в настройках теперь не исчезает молча, а объясняет, что
именно происходит.

Если список пуст и в Chrome — почти всегда это значит, что страница ещё не
получала разрешение на микрофон: без него браузер прячет и динамики.

## Про кэш и версии

Две меры, чтобы браузер никогда не собрал франкенштейна из новой разметки и
старого кода — от такого несовпадения приложение падает молча.

* Всё отдаётся с `Cache-Control: no-cache`: браузер каждый раз проверяет
  свежесть и почти всегда получает пустой ответ `304`.
* Адреса скриптов и стилей внутри страницы содержат отпечаток сборки —
  `/app.js?v=a1b2c3d4e5`. После любой правки адрес меняется, и отдать старое
  из кэша становится физически невозможно.

Отпечаток считается из содержимого файлов и виден в двух местах: внизу
настроек в звонке и по адресу `/api/health`. Совпадают — работает та версия,
которую вы ожидаете.

Один раз может понадобиться **Ctrl+F5**: файлы, закэшированные ещё до этой
схемы, браузер держит до суток, вообще не обращаясь к серверу.

## Если звонок не подключается

Надпись под индикатором показывает, на какой именно стадии он стоит:

| Что написано | Что происходит |
|---|---|
| Соединяюсь с сервером… | Открывается WebSocket к сигнальному серверу |
| Вхожу в комнату… | Сервер отвечает, идёт вход |
| Спрашиваю доступ к камере и микрофону… | Ждём разрешения браузера |
| Ждём собеседника | Всё в порядке, комната пуста |
| Устанавливаю соединение… | Идёт обмен и проверка сетевых путей |
| На связи | Готово |

Соединение с сервером начинается **раньше**, чем запрашивается камера. Это
важно: занятая другой программой камера умеет не отвечать вовсе, и раньше
такой звонок навсегда застревал на «Подключении». Теперь запрос устройств
ограничен двенадцатью секундами, звонок поднимается и без них, а камера
прикрепляется сама, как только освободится.

Если после появления собеседника соединение не встаёт за пятнадцать секунд,
приложение молча пересобирает его само. Не помогло за тридцать — честно
пишет «Не удалось соединиться» и объясняет, что почти всегда виноват VPN или
строгий фаервол.

## Если картинка замирает

Живость видео определяется по счётчику декодированных кадров, а не по
служебному сообщению о состоянии — потерянное сообщение больше не прячет
живую картинку под заглушкой. Если кадры действительно перестали приходить на
шесть секунд или потери перевалили за четверть пакетов, приложение само
пересобирает соединение (`restartIce`), но не чаще раза в двадцать секунд.
Вручную то же самое делает кнопка «Переподключить связь» в настройках или
клавиша `R`.

## Журнал

В панели «Качество» есть вторая вкладка — **Журнал**. Туда пишутся события
соединения: открытие сигнального канала, вход в комнату, смены состояния ICE,
выбранный сетевой путь, обрывы, пересборки, ошибки устройств. Всё со
временем и цветом: красное — отказ, жёлтое — тревожно, зелёное — хорошо.

Кнопка **«Скопировать для отправки»** собирает отчёт: версия сборки, браузер,
комната, текущее состояние, маршрут, разброс пинга и вся история. Ничего
никуда не отправляется само — только в буфер обмена, дальше решаете вы.

## Когда связь обрывается

`restartIce` помогает, пока транспорт жив. Когда он закрылся — а именно так
бывает после сна телефона, смены сети или долгого разрыва — нужна полная
пересборка соединения, причём **одновременно на обеих сторонах**: иначе одна
будет ждать предложение, которого никто не пришлёт.

Это делается тремя путями:

* **Автоматически.** Состояние `failed` запускает пересборку через две с
  половиной секунды.
* **При возврате в приложение.** iOS выгружает медиа, когда гаснет экран;
  вернулись — проверяем состояние и, если оно уже не живое, пересобираем.
  То же самое при восстановлении страницы из кэша Safari.
* **Кнопкой «Перезапустить звонок у обоих»** в настройках. Она шлёт команду
  собеседнику, и оба пересобирают связь с нуля.

## Плохая связь и VPN

VPN ломает звонок тремя способами, и все три теперь видны в панели статистики.

* **UDP закрыт** — соединение уходит на TCP, и это написано в строке
  «Маршрут». По TCP видеопоток живёт заметно хуже: любая потеря вызывает
  повтор и рывок вместо мгновенного пропуска кадра.
* **Прямое соединение не строится** — трафик идёт через ретранслятор, что
  всегда добавляет задержку.
* **Выбран не тот сетевой интерфейс** — строка «Ваш адрес в соединении»
  показывает, с какого адреса вы говорите. Адреса вида `26.x`, `25.x`,
  `100.64–100.127` — это Hamachi, Radmin VPN, Tailscale и подобные; если
  звонок идёт через них, приложение об этом прямо скажет.

Сам факт туннеля браузеру недоступен, поэтому вместо угадывания приложение
показывает три этих признака и объясняет их простым языком.

Если у одного VPN, а у другого нет, прямой путь может не найтись вовсе —
тогда нужен ретранслятор. Поле для своего TURN-сервера есть прямо в
настройках: адрес, пользователь, пароль. Хранится только в браузере и
применяется при следующей пересборке связи.

## Нестабильный пинг

Мгновенное число врёт: пинг может прыгать вдвое между секундами, и по нему не
понять, ровный канал или рваный. В панели «Качество» есть график за последнюю
минуту с минимумом, средним и максимумом. Если разброс переваливает за 90 мс,
приложение прямо пишет, что канал рваный — так ведут себя мобильный интернет,
Wi-Fi на пределе дальности и VPN.

Что делается автоматически:

* **Режим «только голос».** Если потери держатся выше 12% и нижняя ступень
  качества уже не спасает, видео выключается, а голос остаётся — слышать
  собеседника важнее, чем смотреть на замерший кадр. Когда сеть успокаивается
  на десять секунд, видео возвращается само.
* **Приоритет голоса** в сети (`networkPriority: high`), а при демонстрации
  экрана камера уходит на низкий приоритет.
* **Пересборка соединения** при замершей картинке или потерях выше 25%.

## Задержка

Пинг в верхней панели — это время оборота пакета до собеседника и обратно.
Оно определяется маршрутом между вами, и приложение на него влиять не может:
Москва — Екатеринбург это честные 30–50 мс, Европа — Азия под 200 мс.

Что действительно влияет и что сделано:

* **Буфер приёма** — самая управляемая часть задержки. Браузер по умолчанию
  копит запас ради плавности. Режим «Низкая задержка» обнуляет
  `jitterBufferTarget` и `playoutDelayHint` — звук идёт быстрее. Он включён
  по умолчанию и сам отступает, когда потери переваливают за 4%: на рваной
  сети короткий буфер вредит больше, чем помогает.
* **Приоритет голоса** — микрофон помечен `networkPriority: high`, при
  демонстрации экрана камера уходит на низкий приоритет.
* **Адаптивный битрейт** — при потерях и росте пинга качество снижается, не
  доводя канал до переполнения, из-за которого задержка растёт лавиной.
* **Строка «Задержка звука»** в статистике показывает половину пинга плюс
  буфер — то, что реально ощущается в разговоре.

Если пинг велик, смотрите в статистике строку «Маршрут». `через TURN-сервер`
значит, что трафик идёт через ретранслятор — это всегда дороже прямого пути.
`прямое P2P` значит, что дело в самом маршруте: помогают провод вместо Wi-Fi,
отключение VPN и близкий по географии собеседник.

## Оптимизация

* Адаптивный битрейт: пять ступеней качества (до 4 Мбит/с сверху),
  переключение по потерям пакетов и пингу — вниз сразу, вверх осторожно
  (через 12 секунд стабильного канала), а на совсем плохой сети — режим
  «только голос».
* Демонстрация экрана предпочитает VP9: на том же битрейте мелкий текст
  читается заметно лучше, чем в VP8.
* Камера и экран включаются заменой дорожки (`replaceTrack`), без повторных
  переговоров о соединении.
* `degradationPreference`: `balanced` для камеры, `maintain-resolution` для
  демонстрации экрана, чтобы текст оставался читаемым.
* Opus с `useinbandfec` и `usedtx` — восстановление потерянных пакетов и
  молчание в паузах.
* `contentHint` для каждого трека: `speech`, `motion`, `detail`.
* В свёрнутой вкладке исходящее видео ограничивается 150 кбит/с и 8 к/с.
* Смена микрофона или камеры через `replaceTrack` — без разрыва соединения.
* Wake Lock не даёт экрану телефона гаснуть во время разговора.
* Статика отдаётся с Brotli, gzip и ETag; всё кэшируется в памяти сервера.
* `restartIce()` при обрыве и переподключение к сигнальному серверу с
  экспоненциальной задержкой.

## Доступ с телефона

Камера и микрофон работают только в защищённом контексте: `localhost` или
HTTPS. Чтобы открыть сайт с телефона в той же сети, нужен сертификат.

```bash
mkdir certs
# любой самоподписанный сертификат, например через mkcert:
mkcert -key-file certs/key.pem -cert-file certs/cert.pem 192.168.1.10 localhost
node server.js
```

Сервер сам подхватит `certs/cert.pem` и `certs/key.pem` и поднимется по HTTPS.
Пути можно задать и переменными `SSL_CERT` и `SSL_KEY`.

## TURN-сервер

STUN-серверов Google хватает для большинства сетей. Если оба собеседника
находятся за строгим NAT (мобильный интернет, корпоративная сеть), соединение
не установится без ретранслятора. Поднимите [coturn](https://github.com/coturn/coturn)
и укажите его:

```bash
TURN_URL="turn:turn.example.com:3478" \
TURN_USERNAME="user" \
TURN_PASSWORD="secret" \
node server.js
```

В панели статистики строка «Маршрут» покажет, идёт ли трафик напрямую или
через TURN.

## Ограничения

* Комната рассчитана ровно на двоих — третьему приходит «комната занята».
* Комнаты живут в памяти сервера и исчезают, когда все вышли.
* Демонстрация экрана недоступна в Safari на iOS — ограничение самой iOS.
